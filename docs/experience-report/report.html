DrawY 首席体验官报告：20 位真实用户 × 3 档思考强度

我扮演 20 位来自不同行业、不太会写提示词的普通用户，在真实浏览器里从首页开始使用 DrawY：选档位、输入需求、看它起稿、回答它的提问、提一次修改、打开创作过程，最后手动把作品标题加上档位前缀。每个案例分别用 medium、high、xhigh 各跑一遍，共 60 次。

  • 日期 2026-11-01
  • DrawY main · 0b6ebf9
  • 绘制模型 gpt-6.1-terra（API，Default 速度）
  • 生图模型 gpt-image-2.5-flare（ChatGPT 账号通道）

一句话结论：DrawY 已经能把普通人一句口语化的需求，变成一张内容准确、画风统一、能直接拿去用的图；但 xhigh 档在长作品上会因为“上下文压缩被截断”而频繁失败，失败后的提示和画面状态都会让用户困惑。

档位建议：默认用 medium。20 个案例里 medium 零失败、首轮平均不到 3 分钟，画面质量与 high 基本相当；high 在少数案例里想得更周到（c04 辅食的质地进阶、c09 精确到分），值得作为“更细致”选项；xhigh 在修复压缩问题之前不建议开放给普通用户。它偶尔画得最好（c08 深蹲的红色纠错箭头、c03 加入肾脏调节），但耗时约为 medium 的 1.7 倍，还有约五分之一的轮次失败。

最该先修的四件事：① 上下文压缩：修正 token 估算，压缩调用用低推理强度、提高输出上限（P0）。这一项就能消除本次全部 11 次失败。② 生图 ID 里的 -- 让图片被移出作品，8 个作品受影响，改两行代码即可修复（P1）。③ 失败时告诉用户“已保存到第几稿”，提供“继续”按钮，不让带运行错误的版本成为最新稿（P1）。④ 用户手动改过的标题不再被 AI 覆盖（P1）。

关键问题（按严重程度）

P0

上下文压缩被截断，导致长作品运行整体失败

60 次体验共触发 37 次上下文压缩，其中 11 次失败（30%），直接造成 xhigh 档 10 轮、high 档 1 轮失败；medium 零失败。成功的压缩也用掉了最多 3,945 个输出 token，几乎顶到 4,096 的上限。原因有两处。① 触发过早：contextSize() 用“JSON 字符数 ÷ 3”估算 token，而上下文里 42.6% 的字符是加密推理内容（encrypted_content，base64），估算比真实值高约 2.5 倍，所以真实输入只有 3.5 万～8.9 万（中位约 5.3 万）token 时就越过了 12.8 万的阈值。② 压缩调用的输出上限只有 4,096，推理强度却沿用作者设置（xhigh），推理把预算用光后响应变成 incomplete，整次运行判为失败。另外，每次压缩让用户多等约 37 秒，压缩后下一轮的缓存命中从 93% 降到 76%。

建议估算改用上一轮 API 返回的 <code>usage.input_tokens</code> 加上新增内容的估算，至少不要把 <code>encrypted_content</code> 按字符计；压缩调用固定用 low 推理强度，输出上限提到 16k；压缩失败时退化为裁掉最早的截图消息，不要让整次运行失败。代码位置：<code>modules/agent/index.ts:215-241</code>。

P1

生图 ID 带“--”时，图片会被悄悄移出作品

生成图的 ID 由英文名转成 slug，代码先去掉首尾连字符、再截到 28 位，截断点落在连字符上时就产生 g-plastic-bottle-and-aluminum--2e8b 这样带 -- 的 ID。而 take() 判断“作品里的数据还在引用哪些素材”时用的正则 /^[a-z0-9]+(?:-[a-z0-9]+)*$/ 不接受 --，于是只要作者这一轮没有在 materials 里显式列出这张图，它就被移出作品快照，画布上出现红字“素材 … 不在作品中”。我扫描了 60 个作品的全部版本，8 个作品（13%）出现过这种坏版本（c02 三档、c14 high/xhigh、c17 三档）。多数在作者看图后修好了，代价是多出几轮修改；c17 xhigh 恰好在坏版本上失败，报错留在了最终画面上。

建议生成 ID 时先截断再去掉首尾连字符（<code>modules/images/index.ts:219-225</code>，<code>materials/library.ts:356-363</code> 的上传 ID 同理）；<code>modules/materials/index.ts:100/102</code> 的 <code>ID</code>、<code>QUOTED</code> 正则放宽为 <code>-+</code>，兼容已经存在的旧 ID。

P1

失败提示让用户背锅，也不说明画面已保存

失败时 Activity.tsx:140 原样显示 run.error，也就是“模型输出被截断，请缩小本轮作品修改范围”。用户只说了一句话，没法“缩小范围”。而且多数失败发生在作品已经保存新版本之后：c13、c14 的画面其实已经改好了，用户却无法判断能不能用。界面上也没有“继续”按钮，只能自己打字说“继续”。

建议失败时说明“已保存到第 N 稿”，并提供“继续完成”按钮（后端已经支持在同一作品上继续，上下文会保留）；错误原因换成用户能懂的话，技术细节放进运行记录。

P1

失败路径不检查画面，坏版本直接成为最新稿

正常结束要经过 finish 里的 requireObserved()：必须看过最新版本，而且截图里没有运行错误。运行失败时这道检查被跳过，最后一次 write_work 的结果原样成为用户看到的作品。c17 xhigh 就停在了一个有运行错误的版本上。

建议运行失败时，如果最新版本还没被看过或截图里有错误，在画布上提示“这一版可能有问题，点此恢复第 N 稿”；运行错误不要以红字画进作品，改成模块位置的“图片缺失”占位。

P1

AI 后续运行会覆盖用户手动改的标题

我给 60 个作品都手动加了档位前缀，其中 4 个在之后的“继续 / 再试一次”运行里又被作者改回了它自己起的标题（c04、c10 xhigh，c18 high、xhigh），只能再改一次。原因有三：store.rename() 只改 works 表，不留版本；ownChanges() 只列出场景和样式的手动修改，不包括标题，作者不知道标题被用户改过；writeWork 收到 edit.title 就直接覆盖。

建议在作品上记一个“标题由用户命名”的标记，之后 <code>writeWork</code> 忽略作者传来的 <code>title</code>；或者至少在 <code>ownChanges()</code> 里加上“用户把标题改成了 X，请保留”。

P2

新内容画进了子场景，用户找不到

c11 追问“和减数分裂对比”时，high 把对比图放进了新场景。App.tsx 收到运行结束事件后只刷新数据，不切换场景，所以画布仍停留在原图，只在标题旁多出一个很小的 ⌄。用户会以为没画。作者提示词鼓励把更多内容放进子场景，这种情况会越来越常见。

档位到底改变了什么

DrawY 的 deliberate() 会把两类轮次临时升到 max 推理强度：回应请求时定立意（或决定要不要提问）的那一轮，以及每次看完截图后评判的那一轮。其余写画法、改作品的执行轮，才用用户选的档位。下表按运行记录统计了 845 个模型轮次：

  • 三档的决策轮用的都是 max，但推理量并不相同。同样标着 max，xhigh 的决策轮平均推理 2,151 token，medium 只有 1,345。请求级的强度设置仍然在起作用，档位越高，“想”得越多。
  • 执行轮的差距更大，但执行轮主要在写代码。xhigh 的执行轮推理量约为 medium 的 2.9 倍，换来的多是更多注释文字和更细的标注，构图很少因此改变。这也是为什么 20 个案例里三档画面经常几乎一样。
  • xhigh 的轮数也更多。首轮平均 9.3 轮，medium 是 7.8 轮。每轮更慢、轮数更多，叠加起来，xhigh 首轮平均耗时约为 medium 的 1.7 倍。轮数多又让上下文更快变长，更容易触发会失败的压缩，这是 xhigh 失败率高的直接原因。

方法与口径

  • 部署：按仓库 AGENTS.md 在本地起素材服务、截图服务和主程序（Node 25）。唯一的环境适配是让截图服务使用容器里预装的 Chromium；PlantUML 服务未启动，本次 60 次运行都没有用到它。
  • 模型配置：按环境变量用管理员账号接入三个绘制模型，名称是“Terra · medium / high / xhigh”。它们都是 gpt-6.1-terra，只有推理强度不同。用户在输入框右下角的模型菜单里选择。按 DrawY 的设计，定立意和看图评判这两类轮次会临时升到 max 推理强度，所以三档的差别主要体现在执行轮次上。
  • 用户：20 个独立账号，每人一个身份。同一个人依次用 medium → high → xhigh 画同一个需求（每档是一个新作品），模拟真实用户“换个档位再试一次”。所以 high/xhigh 常常复用 medium 生成过的私人素材，生图成本因此偏低，三档之间并不完全独立。
  • 操作：Playwright 驱动真实界面，不调用后端 API 代替用户操作。脚本像真人一样选模型、在输入框里打字、按回车；遇到提问时按这个人的习惯回答（点“你来决定”、选第 1 项或自己写）；成品出来后提一次修改；失败时像真人一样说“继续”；最后点击标题加上【档位】前缀。创作期间每 12 秒截一张图。
  • 耗时：指从按下发送到运行结束、用户在界面上看到结果的实际等待时间。“首个画面”指运行开始后第一次出现构图草稿的时间。
  • 成本：token 用量取自 DrawY 运行记录（trace）。gpt-6.1-terra 按标准价计算：输入 $1/M、缓存输入 $0.05/M、输出 $5/M（推理计入输出）。DrawY 同一用户的请求共用缓存键，平均缓存命中约 83%。生图走 ChatGPT 账号通道，实际不按次计费；为便于比较，按官方 $30/M 图像输出 token 估算，每张约 $0.06。
  • 评估：每一张成品我都看过，并把三档截图拼成对照图逐一比较。凡是涉及数字、法规、医学、地理、规则的内容，我都按公式或公开规定复核过。

我的思考

DrawY 的国际化做得扎实。对这种"信息密集的时间线"，medium 已经足够；更高档位的价值体现在"想得更周到"的注释上，而不是画面本身。

优化建议

  1. 时间线类图表应支持"只看我的学校"的筛选交互（ED/RD 不同学校日期不同）。
  2. 手机竖屏版本：把甘特图转成纵向时间轴。
  3. 对英文用户，下载文件名、作品默认标题也应保持英文（目前一致，值得保持）。
